# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Ticket prefixes and infra-kit commands are in the generated block below — not repeated here.

## Deployments: agents prepare, humans launch

Deploys belong to **infra-kit**, which owns the rules — notably that `prod` is _delivered_, never
deployed ad-hoc (`assertDeployable` refuses it). Reaching the workflow-dispatch endpoint directly
skips every one of those rules, so a raw dispatch is not a shortcut — it is a way to get them wrong.

`.claude/hooks/README.md` is the map: every hook, what it refuses, which way it fails, and where each
rule switch lives. It is pinned by `__tests__/hook-map.test.mjs`, so it cannot drift from the code —
read it first.

Two layers refuse deploys, and both are live. `.claude/hooks/block-deploy.mjs` (behind
`bash-launcher.mjs`) is the **precise** layer and wins wherever they disagree, because it parses argv
positionally and sees through env prefixes, `sudo`, and shell wrappers. The `permissions.deny`
entries in `settings.json` are **defence in depth**: they match a command prefix only, but they
survive the hook file being deleted, which is the one gap the hook cannot cover. The list below
describes the hook; if it and the hook ever diverge, the hook wins and this text is the bug.

**Allowed:**

- read workflow state freely — `gh run list` / `view` / `watch`, `gh workflow view`, `gh api` GETs
- **deploy to non-prod** — expected, not merely tolerated. `ik release deploy-all --json --agent` /
  `ik release deploy-selected --json --agent`: both preview the plan and exit; re-run the same argv
  with `--yes` to execute. Both enforce the same rules: `prod` is refused, every other environment
  is fair game.

**Refused by the hook:**

- the `/dispatches` endpoint by any route — `gh api`, `curl`, `wget`, or a URL assembled from
  variables.
- `gh run rerun` — the run being repeated may have been a deploy, so re-running one deploys.
- `ik release deliver`, `dx-release-deliver`, `release-deliver` — delivery merges the release PR into
  `main` with `--admin` and deploys `prod`. Irreversible, and a human's call.

`gh workflow run` is **not** currently refused (`BLOCK.ghWorkflowRun` is off in the hook), but prefer
the infra-kit command regardless — that is the path carrying the rules.

When a release is ready, stop and hand off:

> Release is ready, CI is green. To deliver: `pnpm dx-release-deliver`

The human runs it from their own terminal or the GitHub UI. These rules bind agents only; they
do not change how a person deploys.

## .claude test suite

Everything under `.claude/**/__tests__/` — hooks and skill scripts alike — is covered by
`pnpm run test:claude`, deliberately **not** part of `pnpm run qa`: the quality-gates hook runs `qa`
on every task completion, so folding its own suite in made each completion pay ~65s to re-verify the
hooks. CI runs it as a separate step. If you change a hook or a skill script, run
`pnpm run test:claude` yourself — nothing else will.

One glob, one script: a second parallel convention would mean two CI concerns and two places to
forget. New project skills that ship scripts get picked up by putting their tests in
`.claude/skills/<name>/__tests__/`.

# infra-kit

This repository uses the **infra-kit** CLI for environment, worktree, and release workflows.
This block is generated by `ik audit --fix --root` — edit text _outside_ the markers, never inside.

## Commands (`ik` = `infra-kit`, the global CLI)

- `ik env-load [-c <config>]` / `ik env-clear` / `ik env-status` — load, clear, or inspect Doppler env vars for a config (e.g. `dev`). Source the returned file to apply. Without `-c`, an agent loads the project's `defaultEnv` (set yours with `ik config-set defaultEnv <env>`); with none set it is refused and must ask the human.
- `ik dev [app]` / `ik dev-status` — run this worktree's dev servers, or report what is running. An app (`ik dev client`) runs its api and ui plus every backend its proxy routes can run locally; no name runs every app. App names are per-repo: an unknown one is refused with the apps as choices, never guess one.
- `ik e2e [--app <app>]` — run an app's Playwright suite locally: against this worktree's dev server when it runs, otherwise the package's `infraKitE2e()` Playwright config starts `ik dev <app> --reuse` for the run and stops it after. Plain `playwright test` / `pnpm e2e-test` behave the same way. `--cloud` runs against the deployed app instead — the URL the loaded env (`ik env-load -c <env>`) holds in the target app's `deployedUrlEnv` — previews, and needs `--yes`; `--dry-run` prints the target.
- `ik worktrees add` / `worktrees list` / `worktrees remove` / `worktrees sync` — manage release and feature git worktrees. `ik worktrees add --feature <name> [--base <dev|main|release>]` creates `feature/<name>` at `<root>-worktrees/feature/<name>`, cut from `dev` by default (the default branch in a repo without `dev`); `worktrees remove --feature <name>` removes it. To close the worktree a session runs in ("close this worktree"), run `infra-kit worktrees remove --self` from inside it: it previews, and its `--yes` re-run hands the removal to an Orca tab of the main checkout, which closes every tab of the worktree — this session included. The `/infra-kit:worktrees` skill is the agent entry point for feature worktrees — never create one with raw `git worktree add` or Claude Code's `EnterWorktree`, which skip `pnpm install`, the editor/Orca wiring and the `feature/` layout.
- `ik release create` / `release remove` / `release list` / `release deploy-all` / `release deploy-selected` / `release deliver` / `release edit` — release-branch and deploy flow.
- `ik release merge-dev` — merge the dev branch into every release branch; `--keep-conflicts` hands off any real conflict to a CLI-owned resolution worktree, `--continue`/`--abort` resume or drop that hand-off. The `/infra-kit:merge-dev` skill is the agent entry point for the whole flow.
- `ik audit` — audit packages against their `infra-kit.config.ts` rules (`--root`: the repo root against the `audit` block in `infra-kit.json`).
- `ik audit --fix` — regenerate this repo's infra-kit guidance blocks (`--all` for every package, `--root` for this file).
- `ik doctor` — check gh / doppler / aws install + auth and repo setup.
- `ik setup` — set up infra-kit on this machine: shell integration, the Claude Code skills plugin, and the external CLIs (brew, git, aws, gh, doppler, portless).

## Conventions

- Tickets are prefixed by area: `[FE]` frontend, `[BE]` backend, `[DO]` DevOps/infra, `[APP]` mobile app, `[IDEA]` proposal, `[ROOT]` cross-cutting. Pick the single dominant area.
- Config is split by level: repo-wide settings live in the root `infra-kit.json` (personal overrides in `~/.infra-kit/`), per-package settings in that package's `infra-kit.config.ts`. The root has no `infra-kit.config.ts`.
- Environment variables are managed through Doppler via `ik env-load` — never commit secrets.
- Every workspace package has its own CLAUDE.md with package-scoped rules — read it before editing that package.
- Launch Claude Code at the repository root: the infra-kit plugin (the `/infra-kit:*` skills) and this repo's `.claude/settings.json` hooks load only from there. If the `/infra-kit:*` skills are absent, this is a subdirectory session — restart Claude Code at the root.

## Agents

- Agents drive the same CLI over Bash: `infra-kit <command> --agent --json`. The `/infra-kit:*` skills are the entry points and they run the CLI on `PATH`.
- A confirm-gated command (`release create|remove|edit|merge-dev|deploy-all|deploy-selected`, `release merge-dev --continue|--abort`, `worktrees add|remove|sync`, `vendor sync`) previews its plan and exits without acting; re-run the same argv with `--yes` to execute. Never put a mutating command behind a prefix allow — that makes the `--yes` re-run unprompted (`ik doctor` warns on such a pattern).
- `env-load`, `env-clear` and `infra-kit setup` have no confirm step and run once: the host's prompt on the argv is the approval. `release deliver` is human-only and is refused under agent mode.
- A command that needs a human choice returns a structured `argument_required` refusal naming the option; pass the value instead of retrying.

## Writing code

- Comment the **why**, never the **what**. If a comment would only restate what the code already says (a name, a type, an obvious assignment), delete it — and if code needs a comment to be _understood_, prefer renaming/refactoring until it reads on its own. Reserve comments for the genuinely non-obvious: external quirks, ordering constraints, fail-safe branches, workarounds, business-logic definitions. Keep them compact. When a comment explains a bug, outage, or upstream issue, link the source of truth instead of describing it.
- Unit tests are `*.test.ts(x)` in a `__tests__/` folder beside the code they test (`src/foo/__tests__/foo.test.ts`), never next to the source file; inside a frontend feature, all of them go in the feature root's `features/<name>/__tests__/`. `*.spec.ts` is only for Playwright specs in an e2e package. The `@wl/test-location` lint rule enforces it.
